# RED demo — подопытный сервис

Маленький HTTP-сервис для лабораторной по мониторингу. Python 3.12, aiohttp,
Prometheus client и OpenTelemetry. Данные не требуют базы; счетчики живут в памяти
одного процесса и обнуляются при его перезапуске.

В комплекте готовый сервис и первый инфраструктурный этап — Compose только
с приложением. Prometheus, Grafana, Loki, Jaeger и Alertmanager здесь пока не
развернуты: их настройка — следующие учебные этапы. Корневой README учебного
репозитория и полный текст части 4 при подготовке были недоступны.

## Первый этап: запустить приложение через Compose

Нужны Docker Engine / Docker Desktop и Docker Compose v2. Распакуй архив,
помести папку `red-demo` в нужный каталог лабораторной и открой в ней терминал.
При первой сборке нужен доступ к Docker Hub и PyPI.

```bash
docker compose up -d --build
```

`--build` собирает образ из Dockerfile, `up` создает и запускает сервис,
`-d` оставляет его работать в фоне. Compose хранит описание запуска в файле,
чтобы среду можно было воспроизвести.

```bash
docker compose ps
```

Показывает состояние контейнера. Через несколько секунд ожидается `healthy`:
healthcheck проверяет HTTP-ответ `/healthz`, а не просто наличие процесса.

Открой <http://localhost:8000>. Публикация `127.0.0.1:8000:8000` означает:
локальный адрес хоста → порт 8000 хоста → порт 8000 контейнера. Внутри контейнера
приложение слушает `0.0.0.0`, чтобы принимать трафик от Docker.
`EXPOSE` в Dockerfile сам по себе не публикует порт.

Если Docker работает на удаленной VM, localhost браузера — твой компьютер,
а не VM. Создай SSH-туннель (замени `user@vm` своими данными):

```bash
ssh -L 8000:127.0.0.1:8000 user@vm
```

Оставь SSH открытым и зайди на <http://localhost:8000> на своем компьютере.

## Что делают кнопки

| Кнопка / URL | Результат |
|---|---|
| «Создать ошибку»: `POST /api/error` | HTTP 500; увеличиваются счетчики запросов и ошибок |
| «Создать задержку»: `POST /api/delay` | HTTP 200 через случайные 1–3 секунды |
| «Нагрузка»: `POST /api/load` | 200 HTTP-запросов к собственному `GET /api/work`, 10 параллельных работников |
| `GET /metrics` | Метрики в текстовом формате Prometheus |
| `GET /healthz` | HTTP 200 для проверки работоспособности |

Нагрузка идет коротким всплеском около 2 секунд плюс накладные расходы.
Это генератор запросов, а не CPU stress test. Ответ содержит `sent`, `succeeded`,
`failed` и длительность. В норме будет 200 успешных внутренних запросов; вместе
с самим `POST /api/load` счетчик всех запросов увеличится на 201.
Повторный запуск нагрузки, пока предыдущий не завершен, вернет 429.

Задержка использует `asyncio.sleep`: медленный запрос ожидает, остальные
обслуживаются. Внутренние запросы направлены на loopback текущего контейнера,
поэтому не требуют внешнего DNS и не создают рекурсивную нагрузку.

Проверки без браузера:

```bash
curl -i -X POST http://localhost:8000/api/error
curl -i -X POST http://localhost:8000/api/delay
curl -i -X POST http://localhost:8000/api/load
curl http://localhost:8000/metrics
```

Каждая команда — отдельный запрос. HTTP 500 в первом случае ожидаем:
это специально созданная ошибка, сервис продолжает работать.

## Метрики и RED

| Сигнал | Метрика | Смысл |
|---|---|---|
| Rate | `http_requests_total{method,route,status}` | Число завершенных запросов; RPS позже вычисляется по изменению счетчика во времени |
| Errors | `http_errors_total{method,route}` | Число ответов 5xx; 4xx ошибками сервера здесь не считаются |
| Duration | `http_request_duration_seconds{method,route}` | Гистограмма длительности обработки в секундах |

Гистограмма экспортируется сериями `_bucket`, `_sum`, `_count`.
Измеряется время работы обработчика, включая искусственное ожидание и ожидание
внутренних запросов. Передача ответа по сети до браузера в эту длительность
не входит. Поэтому время на странице может быть немного больше.

`/metrics` и `/healthz` исключены из RED, логов запросов и трейсов.
Label `route` содержит маршрут, а для неизвестных URL — `unmatched`;
произвольные URL и trace_id не попадают в labels метрик. Это ограничивает
число временных рядов. До первого обращения к маршруту его серии могут отсутствовать.
Стандартные метрики процесса/Python также доступны.

## JSON-логи

```bash
docker compose logs -f app
```

`-f` продолжает показывать новые записи. Приложение пишет по одному JSON-объекту
на строку в stdout. Compose может добавлять свой префикс; для чистого вывода:

```bash
docker compose logs --no-log-prefix --no-color app
```

Запись о запросе содержит `timestamp`, `level`, `message`, `service`,
`trace_id`, `span_id`, `method`, `route`, `status`, `duration_seconds`.
Для 5xx уровень — ERROR, для обычных ответов — INFO.
У служебных записей старта/остановки `trace_id: null`: они не принадлежат запросу.

## Контракт для последующего подключения трейсов

Инструментация выполнена вручную официальным OpenTelemetry SDK:
входящий запрос создает SERVER span; задержка — дочерний span;
исходящие запросы нагрузки — CLIENT spans. Заголовок W3C `traceparent`
передается в запросы к себе и извлекается на входе. Поэтому у одной нагрузки
и ее внутренних запросов общий trace_id, но разные span_id.
Ответ 5xx отмечается статусом ERROR в трейсе.

Текущий trace_id возвращается в `X-Trace-ID` и показывается на странице:
его можно сопоставить со строкой JSON-лога и впоследствии найти в Jaeger.
Выбран режим записи всех трейсов, подходящий для маленькой лабы.

Экспорт — OTLP/HTTP protobuf. Без адреса приемника spans и trace_id создаются,
но не сохраняются во внешнем хранилище. Это позволяет запустить приложение
до настройки Jaeger.

| Переменная | Назначение |
|---|---|
| `OTEL_SERVICE_NAME` | Имя сервиса в трейсах; по умолчанию `red-demo` |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Базовый адрес OTLP/HTTP приемника; SDK добавляет `/v1/traces` |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | Альтернатива: полный URL трейсов с `/v1/traces`; задается приложению напрямую |
| `PORT` | Внутренний HTTP-порт; по умолчанию 8000 |

При подключении приемника в той же сети Compose базовый адрес может иметь вид
`http://jaeger:4318`, если так назван и настроен его сервис. `localhost` внутри
контейнера приложения указывает на само приложение, а не на соседний контейнер.
Текущий Compose передает базовый endpoint из одноименной переменной окружения
или `.env`; по умолчанию он пустой. Настройки полного URL и другого PORT
потребуют соответствующего изменения Compose, портов и healthcheck.
